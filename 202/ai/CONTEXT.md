# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

PrestaShop module `shoppingfeed` (module 2.x, PrestaShop 1.7.6+ through 9.x, PHP 7.1+; code must stay syntax-compatible with PHP 7.1, CI lints on 7.1/7.4/8.2). It syncs product feeds, stock and prices to ShoppingFeed and imports marketplace orders into PrestaShop. The repo is meant to be cloned into `<prestashop>/modules/shoppingfeed`; most code depends on PrestaShop core classes and can't run on its own.

- PRs target the `develop` branch.
- Module version: the single source of truth is `TARGETVERSION` in `202/build.xml`. Packaging (`.github/workflows/zip.yml`) replaces the `@version@` placeholder everywhere with it, so never edit `$this->version` in `shoppingfeed.php` (it stays `@version@`). `config.xml` is generated by PrestaShop and git-ignored (`/config*.xml`); don't commit it.
- A change that adds `upgrade/install-X.Y.Z.php` must also set `TARGETVERSION` to `X.Y.Z`, otherwise the upgrade script never runs on shops updating to the packaged zip. X.Y.Z must be higher than the latest existing script in `upgrade/`.
- Coding standard: PrestaShop coding standards (via `prestashop/php-dev-tools`, configured in `.php-cs-fixer.dist.php`).

## Commands

```bash
# Code style (CI runs the dry-run version)
vendor/bin/php-cs-fixer fix
vendor/bin/php-cs-fixer fix --dry-run --diff --using-cache=no

# PHPStan (level 5) needs PrestaShop sources, so it runs in Docker. CI (.github/workflows/php.yml)
# runs two pairs; the PS image and the PHPStan image must match (PS latest needs PHP 8.1):
#   PS=1.7.4.0  PHPSTAN=phpstan/phpstan:0.12
#   PS=latest   PHPSTAN=ghcr.io/phpstan/phpstan:1-php8.1
# Use a volume per PS version: a named volume is only filled on first use, so reusing one keeps old sources.
PS=latest; PHPSTAN=ghcr.io/phpstan/phpstan:1-php8.1   # run again with the 1.7.4.0 pair
docker run -tid --rm -v sf-phpstan-$PS:/var/www/html --name temp-ps prestashop/prestashop:$PS
docker exec temp-ps rm -rf /var/www/html/modules/shoppingfeed
docker run --rm --volumes-from temp-ps -v $PWD:/var/www/html/modules/shoppingfeed \
  -e _PS_ROOT_DIR_=/var/www/html --workdir=/var/www/html/modules/shoppingfeed \
  $PHPSTAN analyse --configuration=/var/www/html/modules/shoppingfeed/202/phpstan/phpstan.neon
docker stop temp-ps

# PHPUnit: integration tests against a real PrestaShop with a DB (CI uses 8.1.5).
# run_for_unittest.sh installs the module, loads fixtures AND runs the whole suite once: that run is the
# reference result. Re-running the full suite in the same container fails the import tests (orders are
# already imported and get skipped), so for a clean full run stop the container and start a new one.
docker run -tid --rm -v $PWD:/var/www/html/modules/shoppingfeed --name temp-unittest-ps 202ecommerce/prestashop:8.1.5
docker exec -t temp-unittest-ps sh /var/www/html/modules/shoppingfeed/202/docker/run_for_unittest.sh

# Single test (inside the container, after run_for_unittest.sh has set up fixtures once)
docker exec -t -w /var/www/html/modules/shoppingfeed temp-unittest-ps \
  php -dmemory_limit=512M vendor/bin/phpunit -c 202/phpunit.xml --filter testImportAmazon
```

`202/docker/run_for_unittest.sh` installs the module and its carrier module dependencies (dpdfrance, colissimo, mondialrelay, nkmgls), then loads SQL fixtures that the tests rely on (carrier mappings in `ps_shoppingfeed_carrier`, rule configuration in `SHOPPINGFEED_ORDER_IMPORT_SPECIFIC_RULES_CONFIGURATION`, taxes, stock, cart rules, an API token). A new test that needs DB state usually means adding fixtures to this script.

`docker-compose.yml` builds a local dev PrestaShop from `202/docker` and mounts the module (port 8080).

## Vendor / autoloading

- `vendor/prefixed/` (Guzzle, PSR, php-http, ShoppingFeed PHP SDK, etc. re-namespaced under `ShoppingfeedPrefix\`) and `vendor/totpsclasslib/` (202 ecommerce's shared lib, namespace `ShoppingfeedClasslib\`) are **committed** and shipped. The prefixing avoids conflicts with other modules' Guzzle versions. They are generated by `202/prefix-vendor-namespace.php`; don't edit them by hand. The rest of `vendor/` is dev-only and untracked.
- Autoloading is `classmap-authoritative`: legacy classes in `classes/`, `controllers/`, `shoppingfeed.php` are classmapped, and `src/` is PSR-4 `ShoppingfeedAddon\`. After adding a class, run `composer dump-autoload`, or it won't be found.
- Tests live in `202/tests/` (namespace `Tests\`); `202/` is excluded from the release zip and from the PHP lint.

## Architecture

**Entry point** `shoppingfeed.php`: the `Shoppingfeed` module class holds all configuration key constants (`Shoppingfeed::ORDER_IMPORT_ENABLED`, …), the hook list, and most legacy hook handlers (product/combination/stock/price updates, order status changes, invoice PDF, etc.). Newer hooks go through `src/Hook/HookDispatcher.php` (classlib's `AbstractHookDispatcher`), whose hooks are merged into `$hooks`.

**Cron / sync controllers** (`controllers/front/syncProduct.php`, `syncOrder.php`, `syncAll.php`) extend `ShoppingfeedCronController` (classlib `CronController`, protected by the module `secure_key`). They can be run from the CLI via `cli.php controller=syncOrder secure_key=… ssl=off`. `controllers/front/product.php` serves the product XML feed (generated with `shoppingfeed/php-feed-generator`, see `src/Services/SfProductGenerator.php` / `ProductSerializer.php`).

**Actions chains** (the core pattern): work is done by `ShoppingfeedAddon\Actions\ActionsHandler` (extends classlib's handler). A caller sets a *conveyor* (shared array of state), lists method names with `addActions(...)`, then `process('shoppingfeedOrderImport')`, which resolves to `classes/actions/ShoppingfeedOrderImportActions.php` and runs each method in order, stopping when one returns false. Other chains: `ShoppingfeedOrderSyncActions` (pushing order status/tracking/invoices back to ShoppingFeed), `ShoppingfeedProductSync{Stock,Price,Preloading}Actions`. The chain class can be overridden by other modules through the classlib process-override hook.

**Order import**: `syncOrder::importOrders()` fetches orders from the API (`classes/ShoppingfeedApi.php` wraps the SDK) and runs the chain `registerSpecificRules → verifyOrder → createOrderCart → validateOrder → (recalculateOrderPrices, acknowledgeOrder, …) → postProcess`. Marketplace/carrier specific behavior is **not** hardcoded in the chain; it lives in *specific rules*:
- `src/OrderImport/Rules/*` extend `RuleAbstract`, implement `isApplicable(OrderResource)` plus any event methods (`onPreProcess`, `onCarrierRetrieval`, `onVerifyOrder`, `onCustomerCreation`, `beforeShippingAddressSave`, `checkProductStock`, `afterCartCreation`, `afterOrderCreation`, `beforeRecalculateOrderPrices`, `onPostProcess`, … full list in `RulesManager::applyRules`).
- Rules are registered through the `actionShoppingfeedOrderImportRegisterSpecificRules` hook. The module's own list is in `Shoppingfeed::hookActionShoppingfeedOrderImportRegisterSpecificRules`, and **order matters** there. Third-party modules can add rules through the same hook.
- Per-rule configuration (admin "Orders feeds" page, `AdminShoppingfeedOrderImportRules`) is stored as JSON keyed by rule class name in `SHOPPINGFEED_ORDER_IMPORT_SPECIFIC_RULES_CONFIGURATION`.
- A new rule needs: the class in `Rules/`, registration in the hook list, and usually a test in `202/tests/OrderImport/` using a JSON API order from `dataset/` (see `AbstractOrdeTestCase::getOrderRessourceFromDataset` and `OrderImportSimpleTest` for the pattern).

- A specific rule whose behavior depends on the carrier must not guess it with `CarrierFinder::getCarrierForOrderImport()` (that ignores the carrier selection rules): use `onVerifyOrder`, which receives the selected carrier in `$params['carrier']` and still runs before the addresses are created (`ColissimoRule`, `ManomanoDpdRelais`), or check `$cart->id_carrier` in `afterCartCreation` (`GlsRule`, `MondialrelayRule`).

**Carrier selection**: the import carrier is chosen in one place, `CarrierFinder::selectCarrierForOrderImport()` (called by `verifyOrder()`). With the global switch `Shoppingfeed::ORDER_CARRIER_ADVANCED_RULES` on, carrier selection rules (`ShoppingfeedCarrierRule`, `src/CarrierRule/`) replace the marketplace↔carrier mapping; off (default), the mapping is used. Design and implementation details: `202/ai/docs/specs/34133.md`.

**Persistence**: ObjectModels in `classes/` (`ShoppingfeedOrder`, `ShoppingfeedProduct` sync queue, `ShoppingfeedTaskOrder`, `ShoppingfeedToken` per shop/lang/currency API tokens, `ShoppingfeedCarrier` marketplace↔PS carrier mapping, `ShoppingfeedCarrierRule` carrier selection rules, `ShoppingfeedPreloading` cached feed data). Install/upgrade uses classlib's `ModuleInstaller`. Schema/hook/configuration changes need a new `upgrade/install-X.Y.Z.php` (`upgrade_module_X_Y_Z($module)`) and `TARGETVERSION` bumped to X.Y.Z in `202/build.xml` (see Project). New configuration keys also need a default in `Shoppingfeed::install()` (`setConfigurationDefault`) for fresh installs.

**Product feed filters**: `src/ProductFilter/` (category/brand/supplier/attribute/feature filters built by `FilterFactory`) restrict which products are exported, configured via `SHOPPINGFEED_PRODUCT_FEED_RULE_FILTERS`.

**Admin**: legacy `ModuleAdminController`s in `controllers/admin/` (extending `classes/ShoppingfeedAdminController.php`), Smarty templates in `views/templates/admin/`, plain JS in `views/js/`.

**Compatibility**: `classes/Compatibility/` (price formatters) is excluded from the composer classmap in `composer.json`.
